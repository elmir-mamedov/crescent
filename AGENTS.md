# Repository Guidelines

## Project Structure & Module Organization

This repository contains Crescent, a lean Markdown knowledge-base viewer. Application code lives in `app/src/` and is organized by responsibility: `server.ts` reads the configuration and starts the server, `content.ts` reads the knowledge-base tree, `frontmatter.ts` parses page metadata, `markdown.ts` renders Markdown, and `views.ts` builds HTML: it re-exports the views from `views/`, one module per feature, each keeping its markup together with the browser script that drives it (the stylesheet is `views/styles.ts`), so new view code belongs in one of those rather than in `views.ts`. The routes live under `server/`, one module per feature (`server/pages.ts`, `server/spaces.ts`, `server/chat.ts` and so on), each registering its routes from the context `server.ts` builds; what several of them draw is in `server/render.ts` and what they read from a request is in `server/http.ts`, so a new route belongs in a feature module rather than in `server.ts`. `kb-writes.ts` makes every write to the KB together with the git commit that records it, and owns the commit subjects; the web server and the MCP server both write through it, each passing only its `via`, so a new kind of write belongs there rather than in a route or a tool. The chat drawer runs the person's own Claude Code or Codex: `agent-cli.ts` (what the two engines share), `claude-cli.ts` (`claude -p`), `codex-cli.ts` (`codex exec`), `chat.ts` (turns, the system prompt, the report of written pages) and `chat-store.ts` (threads, and the images attached to their messages, under `<KB_DIR>/.kb25/chat`). Runtime package files are in `app/`.

The app was called KB25 through 0.12.0, and KB25 stays its internal name. Rename only what people see: page text, window titles and menus, the installer's messages, `Crescent.app` and `Crescent.lnk`. Keep the `kb25` spelling everywhere else, because installed copies and stored data depend on it: the `KB25_*` environment variables (an update from 0.12.0 hands the new installer `KB25_UPDATE` and `KB25_HOME`), the install folders, `kb25.zip`, the `KB25`/`KB25.exe` executable and the `local.kb25.viewer` bundle id (the macOS window's storage and position hang on it), `.kb25/` and `~/.config/kb25/`, browser storage keys, the `kb25:note` marker, the `kb25` MCP server id, and the feedback app id.

In a checkout, `kb/` holds the sample KB the dev server opens: two spaces on quantum mechanics, copied from `app/dev/seed/`, which `npm run dev` makes on its first run and `npm run dev:reset` makes again from scratch. Keep no real pages there. The server refuses the KB an installed Crescent on the same computer uses (`KB25_DEV_REAL_KB=1` overrides that), and `dev:reset` deletes only a KB it made itself. To change what the sample shows, edit `app/dev/seed/`; `src/dev-kb.test.ts` checks that every link, section anchor, image, label and note in it resolves. Each top-level folder under `kb/` is a **space** and its own git repo (`kb/<space>/.git`); `kb/` itself is not versioned. Folders are navigation sections, `index.md` files are section landing pages, and leaf pages use lowercase hyphenated filenames such as `kb/engineering/runbooks/deploy.md`. Assets belong under each space's own `kb/<space>/_assets/` and are referenced with the portable relative form `_assets/file.png` (rewritten to `/<space>/_assets/file.png` at render time). Root files such as `first-step.md` and `knowledge-base-plan.md` are planning/spec notes.

Feedback comes from [`@elmir-mamedov/feedback`](https://github.com/elmir-mamedov/feedback), a dependency pinned to a release tag in `app/package.json`: it draws the viewer's feedback dialog (loaded from `/_vendor/feedback/`, mounted by `FEEDBACK_SCRIPT` in `views/corner.ts`), and `app/src/feedback.ts` uses its outbox to send each report to the shared relay (the private `elmir-mamedov/feedback-relay` repo), which files it as an issue in the private `elmir-mamedov/kb25-feedback` repo. The report format and limits live in that package; change them there, release it, and bump the tag here. `relay/` is the old KB25-only Worker, kept running for copies of KB25 0.3.0 and earlier, which post to it; don't build on it, and retire it once those copies have updated (`relay/README.md` covers it).

## Build, Test, and Development Commands

Run commands from `app/`:

- `npm install` installs runtime and TypeScript tooling.
- `npm run dev` starts the viewer with `tsx watch` at `http://localhost:4000`, on the sample KB in `kb/` (made first if it is missing).
- `npm run dev:reset` replaces `kb/` with a fresh copy of the sample KB, after a test that changed it.
- `npm start` runs the server once without watch mode.
- `npm run app:install` installs `~/Applications/Crescent Dev.app` (macOS), a Spotlight-launchable app that starts this checkout's server if needed and opens Crescent's own window (see Installer & Releases). Its own name and bundle id (`local.kb25.viewer.dev`) keep it apart from an installed `Crescent.app`.
- `npm run typecheck` runs `tsc --noEmit`; use this as the primary verification step.
- `npm run build:shell` builds KB25's native windows into `shell/build/`, each where its tools are: the macOS one with `swiftc`, the Windows one with the .NET SDK (on any system). `--require mac,windows` fails instead of skipping.
- `npm run build:release` builds `dist/kb25.zip`, what the one-line installer downloads; it builds both windows, so it runs on macOS with the .NET SDK (`DOTNET` names a `dotnet` not on `PATH`).

There is no build step for development; TypeScript runs directly through `tsx`. Only a release bundles: `build:release` turns `src/server.ts` and `src/mcp.ts` into single files under `server/` in `kb25.zip`. An installed copy registers that `mcp.mjs` with Claude Code and the Claude app, and its chat runs it too, so a release is how a fix to the MCP server reaches people. The page-writing skill lives in `app/skills/`; the release ships it and setup copies it into `~/.claude/skills/`.

## Installer & Releases

People who are not developers install Crescent with the one-liners in the root `README.md`. `app/installer/install.sh` (macOS) and `app/installer/install.ps1` (Windows) download a private Node.js and the latest release's `kb25.zip`, then run `app/installer/setup.mjs`, one wizard for both systems, where every question is a `[Y/n]`. Every install and update trims that Node.js to its `node` program (no npm, no headers), so nothing an installed copy runs may count on npm. An installed copy runs with sign-in off (`AUTH_DISABLED=1`, loopback only) and keeps working without git. It listens on the first free port from 25250 (written to its `.env`), clear of the 4000 that dev servers, this checkout's included, start on. An install or update moves a copy that KB25 0.5.0 or earlier put on 4000–4099 there, and the restarted server answers the old port for five minutes (`KB25_MOVED_FROM`), so the page that started the update finds the new version; drop that move once those copies have updated. Keep the wizard's questions few and Enter-safe; anything a person must type is a bug. `KB25_UPDATE=1` runs the same installer unattended, for updates: no terminal, every question answered no (an update never changes an install-time choice), and Crescent restarted on the new version: an open window is closed the way quitting closes it and opened again, and with no window open the server restarts in the background. Any new question must still make sense answered no.

KB25's window is a native app around the system's web view (`app/shell/`): `mac/KB25.swift` (WKWebView) is `~/Applications/Crescent.app` itself, and `windows/Program.cs` (WebView2, .NET Framework 4.8) is `KB25.exe`, which setup copies out of `app/` into `<KB25_HOME>/shell/<version>/`, because Windows locks a running program's files and an update replaces `app/` while the window is open. The window runs the launcher (`app/installer/launcher.mjs`), which starts the server unless one answers and prints its address, and opens that address. The address is `/_launch`: while a newer release is out, an installed copy opens there on the update gate, which installs it before the app opens and lets the person in on the old version only if the update fails; otherwise it goes straight to `/`. Until that first page has loaded, the window stays hidden behind a small loading window, `app/shell/splash.html`, which `build:shell` builds into both. Closing the window, or quitting it, sends `POST /_quit?when=idle`; the power button stops the server, which says `quit` on `GET /_window`, and the window closes. A server restart ends that stream without `quit`, so the window stays open and listens again; an update goes further and restarts the window too (`setup.mjs`), so that the new version's window code runs. The windows send links that leave KB25, and links asked for in a new window, to the default browser, and allow only http(s) and mailto there. Both are built by `npm run build:shell` and shipped in `kb25.zip`; CI builds each on its own system, and the release smoke test opens the installed one.

To release: once every change on the release branch (see Commit & Pull Request Guidelines) has been tried by hand, bump `version` in `app/package.json` and `app/package-lock.json` in a last pull request into it, from `chore/release-0.23.0` (`chore: release 0.23.0`), merge the release branch into `main` through a pull request, then tag the merged commit on `main` and push the tag (`git switch main && git pull && git tag v0.23.0 && git push origin v0.23.0`) when asked to push, and delete the release branch. The release workflow refuses a tag that is not on `main`. When people must do something after updating to it (restart the Claude app or Claude Code to load a changed MCP server, say), give the version a message in `app/src/update-messages.ts`, in the change that makes it necessary, keyed by its release branch's version: the installer records each update in `<KB25_HOME>/updated.json`, and the new version's pages then show a card in the bottom-right corner, until it is closed, with that message and a link to the release notes. `.github/workflows/release.yml` builds the zip, installs it for real on macOS and Windows runners, updates it in place with `KB25_UPDATE=1`, smoke-tests it (`app/scripts/smoke-installed.mjs`), and only then publishes the GitHub Release the one-liners download: `kb25.zip`, `install.sh`, `install.ps1`, and `VERSION`, which installed copies read to learn that a newer release is out. `.github/workflows/ci.yml` runs typecheck and tests on Linux, macOS and Windows for every pull request, into the release branch and into `main` alike, and every push to `main`; `main` requires those checks to pass before a pull request merges.

## Coding Style & Naming Conventions

Use TypeScript ES modules, strict types, semicolons, double quotes, and two-space indentation to match the existing code. Keep modules small and focused. Prefer Node standard-library APIs and existing local helpers before adding dependencies.

For content, use lowercase hyphenated Markdown filenames because paths become URLs. Put display titles and optional tags in YAML frontmatter; do not encode human-readable titles in filenames.

## Testing Guidelines

Tests use Node's built-in runner (`node:test`) executed through `tsx`; run them with `npm test` from `app/`. Test files live next to the code they cover as `src/*.test.ts`, and shared setup (throwaway KB dirs, git identity) is in `src/test-helpers.ts`. No extra dependencies are required. Before submitting code, run `npm run typecheck` and `npm test`. A change is tried by hand on the sample KB, in KB25's native window first, because that is where people use it: start `npm run dev`, then open Crescent Dev (installed once with `npm run app:install`), whose window uses that server, so it runs your latest edits. Opened without `npm run dev`, Crescent Dev starts a server of its own that does not watch, and only picks up a change once the power button has stopped it. Try the change itself and what it touches. A browser at `http://localhost:4000` is the fallback, for where there is no dev window: `app:install` is macOS-only, so on Windows and Linux the browser is the hand test. An agent finishing a change offers this to the maintainer rather than deciding it (see Commit & Pull Request Guidelines).

## Commit & Pull Request Guidelines

Work on a branch, never on `main` or the release branch. Start each piece of work on a branch named `<type>/<short-name>` (`feat/inline-notes`, `fix/sidebar-scroll`) cut from the up-to-date release branch, or from an up-to-date `main` when no release branch is open, and if you find yourself on either with changes, branch before committing. `main` is protected on GitHub: it takes no direct pushes, force-pushes or deletion, only pull requests whose CI passed on Linux, macOS and Windows.

Changes reach `main` through a release branch, `release/<version>`, named for the version it will ship as (`release/0.23.0` while `main` is at 0.22.0); one is open at a time, and `git branch -r --list 'origin/release/*'` after a `git fetch origin` shows it. Nothing goes straight to `main`, and nothing is committed or pushed onto the release branch itself: every change, the version bump included, reaches it through a pull request, which the agent that made the change merges itself once CI has passed. The maintainer then tries every change on the release branch by hand together, usually on a weekend, and only then merges it into `main` and cuts the release from there (see Installer & Releases); do not open that pull request, merge into `main` or tag a release unless asked.

When a change is finished and committed, with `npm run typecheck` and `npm test` passing, ask the maintainer one question: open Crescent Dev on this branch for them to try, or open the pull request and merge it into the release branch now? (For a change with nothing to try, such as docs or tests alone, ask only about the pull request.) Then:

1. **Try it first:** start `npm run dev` in the background from this checkout and open the window with `open -a "Crescent Dev"`. The window opens whatever server answers on port 4000, so stop any other dev server there first, and run `npm run app:install` again first if the change touches `app/shell/`. On Windows and Linux, where there is no Crescent Dev, give them `http://localhost:4000` instead. Fix and commit what they find, then ask again; once they are satisfied, stop the dev server and go on with step 2.
2. **Catch up with the release branch:** `git fetch origin`, then check that the open release branch has not moved since you branched (`git merge-base --is-ancestor origin/release/0.23.0 HEAD` fails when it has) and has not been merged and replaced by the next one. If it has, rebase onto the open one (`git rebase origin/release/0.23.0`) and run `npm run typecheck` and `npm test` again. If no release branch is open, cut one from an up-to-date `main` (`git switch -c release/0.23.0 origin/main`) and push it.
3. **Open the pull request and merge it:** push the branch, open its pull request against the release branch (`gh pr create --base release/0.23.0`), wait for CI (`gh pr checks <number> --watch`), and once every check has passed, merge it with `gh pr merge <number> --rebase --delete-branch`. Never merge with a check failing or still running, and do not use `--auto`, which merges at once on a branch that requires no checks. If a check fails, fix it, squash the fix into the commit it belongs to, push with `--force-with-lease` and wait again; if the merge is refused because the release branch moved, go back to step 2. Then give the maintainer the merged pull request's link.

Commit as you work. Every significant change — a feature, a fix, a refactor, a docs or content update — lands on the branch as its own commit once `npm run typecheck` and `npm test` pass. Do not leave finished work sitting uncommitted for someone else to stage, and do not roll unrelated changes into one commit. Stage deliberately with explicit paths (`git add app/src/views.ts`), not `git add -A`, so the diff matches the message. Committing is expected; pushing is not — push the branch, and open and merge its pull request, only when the maintainer says so, which the question that ends each change (above) asks.

Pull requests merge with **Rebase and merge**, so each commit lands on the release branch, and from there on `main`, as written: keep every commit on the branch one finished, passing change, and squash fixups into the commit they fix before the merge.

Write messages as [Conventional Commits](https://www.conventionalcommits.org): `<type>(<scope>): <description>`. Commits made before this convention was adopted do not follow it; leave them alone and apply it going forward.

- **Type:** one of `feat`, `fix`, `docs`, `refactor`, `test`, `perf`, `chore`, `build`, `ci`, `revert`. Pick by what the change does to the product, not by which files it touches — a fix that only edits a test is still `test` if the behaviour did not change.
- **Scope:** optional but preferred, and it names the module or area rather than a path: `server`, `content`, `markdown`, `frontmatter`, `views`, `mcp`, `kb`.
- **Description:** imperative mood, lowercase, no trailing period, and keep the whole subject line under 72 characters. `feat(markdown): add =WxH image size syntax`, not `feat(markdown): Added =WxH image size syntax.`
- **Body:** separated from the subject by a blank line and wrapped at 72 characters. Say why the change was needed and what it does about it; the diff already shows how. Omit the body only when the subject genuinely says everything.
- **Breaking changes:** mark them with `!` before the colon (`feat(mcp)!: rename the token parameter`) and describe the break in a `BREAKING CHANGE:` footer.
- **Trailers:** none otherwise. Never add `Co-Authored-By`, `Generated with`, or any other attribution or tooling footer.

For knowledge-base auto-commits, `kb/README.md` documents the pattern `Update engineering/runbooks/deploy.md via web`.

Pull requests should include a short summary, verification steps, affected paths, and screenshots for UI changes. Link relevant issues or planning docs when applicable.

## Security & Configuration Tips

Configuration is via environment variables: `KB_DIR`, `PORT`, `HOST`, `SITE_TITLE`, the required `AUTH_USERNAME` / `AUTH_PASSWORD` / `AUTH_SESSION_SECRET` (or `AUTH_DISABLED=1` instead, which the server refuses unless `HOST` is loopback), the optional `TRUST_PROXY`, `KB25_CLAUDE_PATH` and `KB25_CODEX_PATH` (the `claude` and `codex` the chat runs, when they are not where the viewer looks), and `KB25_DESKTOP=1`, which the launchers set (KB25.app, the Start-menu shortcut): a server started with no terminal takes `POST /_quit` (KB25's window sends `?when=idle` when it closes, which waits for a running chat turn; without it, it is the power button, which also closes the window through `GET /_window`, the stream the window listens on); it applies only on a loopback `HOST`. The default `HOST=localhost` binds loopback only, so the viewer is reachable from this machine and nowhere else; keep it there. Sign-in is one static credential pair behind a failed-attempt cooldown, so a wider bind publishes a guessable form, in cleartext unless something in front of it terminates TLS. With sign-in off there is no session to protect a request, so the server instead refuses any `Host` that is not loopback (DNS rebinding) and any write whose `Origin` is another site (forged form posts); keep new routes behind that hook. Do not commit secrets from `.env`.

Content that reaches the KB — pulled from a space's remote, copied in, or written by an agent — is untrusted, and three rules keep it inert; keep new code inside them. Frontmatter is read only through `frontmatter.ts`: a plain `---` header on js-yaml's safe schema, never a parser that picks an engine from the file (gray-matter's `---js` ran headers through `eval`). Assets go out only through `/<space>/_assets/*`, whose headers (`assets.ts`) download anything a browser could run and sandbox the rest. And KB25 follows no symbolic link inside the KB: reach files through `Content.resolve`, `resolveAsset` or `fileState`, not by joining a path and handing it to `fs`.
