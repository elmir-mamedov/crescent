# KB Page Authoring

## The core idea: the page is the deliverable, not the chat

When someone asks you to write or update a KB page, the thing they actually want is the **page** — a durable, well-structured Markdown document that lives in the knowledge base and that they, their teammates, and future readers will open and read *there*. The chat window is not where that content is meant to live.

The most common failure mode — and the reason this skill exists — is finishing the write and then re-explaining the same material back in the chat: restating the sections, summarizing what the page says, walking the user through "what I wrote." That duplication burns tokens and wall-clock time for zero benefit. Nobody reads a paragraph-for-paragraph echo of a page they can open in one click. It doesn't even serve validation: the way to check the work is to **open the page and read it**, not to trust a recap generated by the same process that just wrote it.

So a good page-authoring turn has a simple shape:

> understand what's needed → write the page well, in one shot → hand back a link and stop.

This principle holds for every KB write, not just brand-new pages.

## Before you write

Move straight to writing when the request is clear enough to act on — a wrong guess is cheap to fix, because any page can be edited or archived afterward, so you don't need to ask permission to proceed.

Ask **one** short question first only when the *what* (scope/content) or the *where* (which space or section) is genuinely ambiguous. A page committed to the wrong place or covering the wrong thing is more expensive to walk back — it's an auto-committed git change — than a single clarifying line up front. Don't turn this into a checklist; one question, then write.

Pick the location deliberately: every page lives inside a **space** (the first segment of its slug). Use `kb_list_pages` or `kb_search` to see where similar pages already live, and file the new one alongside them rather than inventing a parallel structure.

## Writing the page

- **New page → `kb_create_page`.** It's single-shot: pass the `title` and the full Markdown `body` in one call. Don't create an empty page and then update it — write the complete body the first time.
- **Existing page → `kb_update_page`.** Read the current source first with `kb_get_page` (`format: raw`) so you preserve its frontmatter and don't clobber content, then send the full replacement Markdown (valid frontmatter with a `title` is required).
- **A reason the diff won't carry → `kb_add_agent_note`.** When you change an existing page and the *why* isn't visible in the result — a figure you corrected, a claim you couldn't verify, one of two readings you had to pick — leave a note on that passage saying so. Quote the words as a reader sees them, not as the source spells them. One note per thing genuinely worth saying, not one per paragraph: the reader resolves each one after reading it, and a page fenced in pink marks is one nobody reads.

Follow the KB's conventions so the page fits in:

- The `title` you pass is slugified into a lowercase-hyphenated URL automatically — put the human-readable title in `title`, not crammed into a filename. Add `tags`/`summary` when they'll help discovery.
- Structure with clear headings and lead with what the reader needs first. Write the page for someone landing on it cold, not as a reply to the current request.
- Reference images and attachments in the portable relative form `_assets/file.png` (it's rewritten to the space-qualified path at render time).
- A **folder** is a pure container with no body — don't try to write prose into one. Use `kb_create_folder` only when you need an empty grouping container.

## After you write — the hand-off

`kb_create_page` returns the created `slug`. Your reply's whole job is to **point the user at the artifact**, not to reproduce it. Keep it to essentially one line:

- the page title, linked to its path (`/<slug>`), and
- *only if* there's a genuine decision the user should know about, one short clause naming it — where you filed it, an assumption you made, or something you deliberately left out.

Then stop. Do **not** restate the sections, summarize the content, list "here's what I covered," or narrate the steps you took. If the user wants something changed, they'll tell you after they've read it — and then you'll be reacting to real feedback instead of guessing at what needs saying.

**Examples**

Good:
```
Created **Deploy rollback runbook** → /kb25/engineering/deploy-rollback
```

Good (a real caveat worth one clause):
```
Created **Q3 pricing** → /kb25/sales/q3-pricing — filed under sales/; move it if you'd rather it live under finance/.
```

Bad (the failure this skill exists to prevent):
```
Created the page. Here's what it covers: first, the rollback runbook explains how to
detect a bad deploy, then it walks through reverting the release, then it describes how
to verify recovery, and finally it notes who to page if… [three paragraphs re-explaining
content that is now one click away on the page]
```

## When the user also asked a genuine question

Some requests are two things at once: "explain X, *and* add it to the KB." Answer only the part that isn't already on the page — the genuinely conversational bit — and keep it tight. Don't answer by pasting back what the page now contains; link to the page for that.
